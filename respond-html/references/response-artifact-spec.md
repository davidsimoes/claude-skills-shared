# Response-Artifact Template — Section-by-Section Spec

How to fill in `templates/response-artifact.html` for plans, proposals, comparisons, audits, recommendations.

## The structure (top-to-bottom)

1. **Sticky toolbar** (auto, no fill needed) — stats + 📋 Copy feedback + Clear + theme toggle. Always visible while scrolling.
2. **Header / eyebrow** — one or two words classifying the artifact: "Plan", "Proposal", "Audit", "Comparison".
3. **H1 title** — what the artifact is about. Specific, not generic. Bad: "Deploy options". Good: "Migrate the Acme app to Vercel Pro".
4. **Subtitle** — one-line framing. The question this artifact answers.
5. **BLUF** — bottom-line-up-front. 1-3 sentences. Reactable.
6. **Sections** — see snippet library below. Each section reactable; decision-blocks and callouts inside also reactable.
7. **Open questions / next steps** — final section. What's unresolved.
8. **Footer** — autogenerated, generation timestamp + skill version.

## Feedback model (v0.2 — the important change)

Every **reactable unit** gets three buttons (✅ approve / 💬 comment / ❌ reject) and a comment textarea (auto-shown when 💬 clicked or any text typed). The reactable units are:

- The **BLUF**
- Every **`<section id="...">`**
- Every **`.decision-block`**
- Every **`.callout`** (decision/tradeoff/risk/recommendation)

The template's JS auto-injects the `.react` component + textarea on any reactable unit that doesn't already have one — so you don't have to add them manually. Just write the section/callout/decision-block as normal and the JS handles the rest.

**Caveat**: auto-generated IDs are stable across reloads of the same file but NOT across re-renders. If the user reacts on an artifact and you re-render it (e.g., after applying his feedback), the auto-IDs may shift if callouts are added or reordered — and his reactions move to wrong elements. To avoid this, see "Stable feedback IDs" below.

### Optional: assign stable `data-feedback-id` + `data-feedback-label`

If you want predictable IDs for the markdown export (instead of auto-generated like `routing__callout-decision-1`), add them explicitly:

```html
<section id="routing" data-feedback-id="routing" data-feedback-label="Routing &amp; delegation">
  <h2>...</h2>

  <div class="decision-block" data-feedback-id="route-default" data-feedback-label="Default route when ambiguous">
    ...
  </div>
</section>
```

Auto-generation does an OK job (uses section ID + element-type + auto-incrementing index, label is derived from h2/q/callout-content). Override only if a section has many similar callouts and you want clearer labels in the export.

### Reactions persist to localStorage

Keyed by pathname. Reactions survive reload. There's a Clear button in the toolbar to wipe.

### Copy feedback → markdown

The toolbar's 📋 Copy feedback button (or ⌘⇧C / Ctrl+⇧+C) builds markdown grouped by section and copies to clipboard. Format:

```markdown
# Feedback — <page title>

Date: 2026-05-13 14:30 · Source: file:///...

## BLUF
✅ approve

## What's new in v0.2
- DESIGN CALL: Dropped the global gutter… → ✅ approve

## How the new reactions work
- TIP: You don't need to react on everything… → ❌ reject — reject because of edge case foo
- EDGE CASE: If you clear a textarea… → 💬 comment — great tradeoff framing
```

the user pastes that back into chat. You read it, act on the rejections/comments, re-render if needed.

## TOC

Generated from the H2 section IDs. Build the `{{TOC_ITEMS}}` list as:

```html
<li><a href="#problem">Problem &amp; scope</a></li>
<li><a href="#options">The three options</a></li>
<li><a href="#recommendation">Recommendation</a></li>
<li><a href="#risks">Risks &amp; open questions</a></li>
```

Section titles short (2-5 words). The sidebar is for scanning. Reactions on a section show a tiny ✅/💬/❌ marker next to the TOC entry — so the user can see at-a-glance which sections still need attention.

## Snippet library

### Section block (no manual reaction component — JS injects)

```html
<section id="kebab-case-id">
  <h2><span class="num">02</span> Section title</h2>
  <p>Lead paragraph that frames the section.</p>
  <p>Body…</p>
  <!-- JS will auto-append .react + .react-comment here -->
</section>
```

### Callouts (also auto-reactable)

Four kinds. Use sparingly — one callout per ~300 words of body text is plenty.

```html
<div class="callout decision">
  <span class="label">Decision</span>
  <p>We're going with X because Y. Reversible: yes/no.</p>
</div>

<div class="callout tradeoff">
  <span class="label">Tradeoff</span>
  <p>X gives us Y but costs us Z. We accept this because [reason].</p>
</div>

<div class="callout risk">
  <span class="label">Risk</span>
  <p>If X happens, Y breaks. Mitigation: Z. Likelihood: low/medium/high.</p>
</div>

<div class="callout recommendation">
  <span class="label">Recommendation</span>
  <p>Do X. Why: short rationale. Cost: estimate. Reversibility: notes.</p>
</div>
```

**Picking which callout**:
- `decision` (green) — a choice already made or being proposed. "We're going with X."
- `tradeoff` (amber) — an accepted cost. "We give up X to get Y."
- `risk` (red) — a thing that could go wrong. "If X, then Y."
- `recommendation` (blue) — what should be done. "Do X."

### Decision block (also auto-reactable)

```html
<div class="decision-block">
  <div class="q">Which deploy target for the Acme rewrite?</div>
  <div class="options">
    <div class="option recommended">
      <h4>Vercel Pro</h4>
      <p>Fastest to ship. €200/mo. Edge by default.</p>
    </div>
    <div class="option">
      <h4>Fly.io</h4>
      <p>Cheaper at scale. More ops overhead. €50/mo + time.</p>
    </div>
    <div class="option">
      <h4>Self-host on Hetzner</h4>
      <p>€20/mo. Most control. Most ops cost. Not recommended.</p>
    </div>
  </div>
  <p style="font-size: 0.9rem; color: var(--ink-soft); margin-bottom: 0">
    Rationale: time-to-ship beats infrastructure savings at this scale.
  </p>
  <!-- JS auto-appends .react component here so the user can ✅/💬/❌ the whole decision -->
</div>
```

### Comparison table (NOT reactable on its own — wrap in a section if you want it reactable)

```html
<table>
  <thead>
    <tr><th></th><th>Vercel Pro</th><th>Fly.io</th><th>Hetzner self-host</th></tr>
  </thead>
  <tbody>
    <tr><td>Monthly cost</td><td>€200</td><td>€50</td><td>€20</td></tr>
    <tr><td>Setup time</td><td>2h</td><td>1d</td><td>1w</td></tr>
    <tr><td>Edge by default</td><td>Yes</td><td>Yes</td><td>No</td></tr>
    <tr><td>Ops overhead</td><td>None</td><td>Some</td><td>Significant</td></tr>
  </tbody>
</table>
```

4 columns max in normal width, 5 if absolutely needed. More than that → switch to multiple smaller tables or comparison-by-criteria format with sections per criterion.

### Open-questions section

The final section before the footer. Bulleted list of things the user needs to weigh in on. The whole section is reactable; if the user wants to react per question, structure each question as a separate callout instead.

```html
<section id="open">
  <h2><span class="num">05</span> Open questions</h2>
  <ul>
    <li>How much traffic do we actually expect in month 1? Recommendation flips if &gt;1M req/day.</li>
    <li>Is the Acme team open to Vercel-specific tooling?</li>
    <li>Do we need EU data residency? Vercel Pro doesn't guarantee it.</li>
  </ul>
</section>
```

If you want one reactable unit per question:

```html
<section id="open">
  <h2><span class="num">05</span> Open questions</h2>
  <div class="callout recommendation">
    <span class="label">Question 1</span>
    <p>How much traffic do we expect in month 1? Recommendation flips if &gt;1M req/day.</p>
  </div>
  <div class="callout recommendation">
    <span class="label">Question 2</span>
    <p>Is the Acme team open to Vercel-specific tooling?</p>
  </div>
  ...
</section>
```

## Length guidance

- **BLUF**: 30-80 words.
- **Each H2 section**: 50-300 words of prose + callouts + tables as appropriate. If a section grows past 300 words, split it.
- **Total reactable units**: aim for 8-20. Fewer than 8 → maybe the artifact is too simple, reply in chat. More than 20 → the user will react-fatigue, split the artifact.

## Filling tokens

Pass through these tokens when substituting into the template:

| Token | Example value | Notes |
|---|---|---|
| `{{TITLE}}` | "Migrate Acme to Vercel Pro" | H1; specific, not generic |
| `{{SUBTITLE}}` | "How to ship the rewrite in 3 weeks without ops debt" | One-line framing |
| `{{EYEBROW}}` | "Plan · 3 weeks" | One short category + flavor |
| `{{BLUF}}` | "Vercel Pro is the recommended path. €200/mo trades off against ~5 days of ops setup elsewhere…" | Bottom-line-up-front, 30-80 words |
| `{{TOC_ITEMS}}` | `<li><a href="#problem">Problem</a></li>...` | One `<li>` per H2 section |
| `{{SECTIONS}}` | Full section HTML | See snippets above |
| `{{ACCENT}}` | `#b1230b` | Light theme accent; see aesthetics.md |
| `{{ACCENT_DARK}}` | `#ff7a59` | Dark theme accent |
| `{{BODY_FONT}}` | `Fraunces` | Body font family name (no quotes) |
| `{{HEADING_FONT}}` | `Manrope` | Heading font family name |
| `{{GOOGLE_FONTS_URL}}` | `https://fonts.googleapis.com/css2?family=Fraunces:opsz,wght@9..144,400;9..144,500&family=Manrope:wght@500;600;700&display=swap` | Full URL with both families and ALL weights used in CSS. For variable fonts with `opsz` axis (e.g., Fraunces, Newsreader, Source Serif 4, EB Garamond), include `opsz,wght@<range>,<weights>` — otherwise the optical-size axis falls back to default metrics and the typography looks slightly off. Manrope weights: include 500/600/700 (template uses 600 for `.option h4` and `.subtitle`). |
| `{{GENERATED_AT}}` | `2026-05-13` | Date string (kept short for footer) |

## Escaping token values

Always HTML-escape `<`, `>`, `&`, `"`, and `'` in token values before substituting — a deal/topic title containing `&` will break the rendered HTML otherwise, and a title with `"` in a `data-feedback-label="..."` attribute will break that attribute. Use `&amp;`, `&lt;`, `&gt;`, `&quot;`, `&#39;`.

**Escape-required tokens** (plain text — `generate.py` runs `html.escape(..., quote=True)`): `{{TITLE}}`, `{{SUBTITLE}}`, `{{EYEBROW}}`, every label inside `{{TOC_ITEMS}}`, AND any explicit `data-feedback-label` you assign.

**Trusted HTML tokens** (NOT escaped — Claude is responsible for valid HTML AND for not interpolating untrusted input): `{{BLUF}}`, every section body inside `{{SECTIONS}}`. Claude may use `<strong>`, `<code>`, `<em>`, `<a>` etc. inside these.

Unicode characters (Czech diacritics, accented Latin, emoji) DON'T need escaping — UTF-8 handles them. Only the 5 HTML special characters above need escaping.

## Stable feedback IDs (recommended for callouts and decision-blocks)

The template's JS auto-generates `data-feedback-id` for any reactable unit without one, using `<section-id>__<element-type>-<auto-counter>` (e.g., `routing__callout-decision-1`). This works fine for the first render but is **brittle across re-renders**: if you add or reorder a callout, the auto-counter shifts and the user's reactions silently move to the wrong element.

**Strongly recommend** assigning explicit, content-derived `data-feedback-id` on every callout and decision-block when you expect the user to react and you might re-render:

```html
<div class="callout decision" data-feedback-id="route-default-ambiguous">
  <span class="label">Decision</span>
  <p>When in doubt, default to response-artifact…</p>
</div>
```

Use kebab-case derived from the callout's gist, prefixed with the section ID. This way the user's reactions survive across re-renders.

## What to skip

- Don't include sections that don't earn their space (a 30-word "Background" section is filler).
- Don't include callouts that just restate the surrounding paragraph.
- Don't include a "next steps" section that says "talk to the user" — that's implicit.

## What to never do

- Don't add the old `.gutter` sidebar or `.section-note` per-section notes — those are removed in v0.2. The inline reaction component IS the feedback system.
- Don't add charts/graphs unless the data really needs them. Charts in plans/proposals usually feel like padding.
- Don't add screenshots/images unless they carry information the text can't.
- Don't auto-include a "References" section unless there's something to link to.
- Don't manually add `.react` + `.react-comment` — the template's JS injects them. Only the BLUF has them in the HTML because it doesn't have a `.bluf` body wrapper.
